# RO. Nation LIVE - Ticket API

> Check whether a ticket is valid, find out what kind of ticket it is, hand one
> out, take one back, and mark it redeemed once it has been scanned at the door.
>
> This file is written for an LLM (or a person) wiring a Roblox experience up to
> the door. Everything here is the real contract - if the code and this file ever
> disagree, the code wins and this file is a bug.

Base URL: https://ronation.live
Auth:     every request needs the header `x-api-key: <key>`
          (`Authorization: Bearer <key>` also works)
Method:   Writes are POST + `Content-Type: application/json`. The reads (events, a
          show's seats, a player's tickets, a hold) are GET; releasing a hold is DELETE.

Enable **Allow HTTP Requests** in Roblox Studio → Game Settings → Security, or
none of this works.

---

## Getting a key

A key looks like this, and it is the whole of your credentials:

```
rnl_k7m2p9x4qz_9f3hd2n8vqw4mzx7rbt6cyk3jphs5nga
    └── keyId ──┘└──────────── secret ─────────────┘
```

Mint one in your portal, under **API keys**:

| Organisation      | Where                                    | Who may mint                          |
| ----------------- | ---------------------------------------- | ------------------------------------- |
| RO. Nation LIVE   | `portal.ronation.live/shasha/keys`       | RNL group rank **245+**               |
| Sleep Token    | `portal.ronation.live/sleeptokenro/keys` | STRO group rank **253+** (Co-Founder and above) |
| Any partner       | `portal.ronation.live/<slug>/keys`       | that partner's managers, or RNL 250+  |

Every address on `portal.ronation.live` now goes through one sign-in first. Open any
of the links above while signed out and you land on **`portal.ronation.live/login`**,
which sends you on to where you were headed once you have signed in with Roblox - so
you can paste a deep link to a keys page at somebody and it will still work.

Signing in is not the same as getting in. Any Roblox account can complete the
sign-in; the rank column above is what decides whether the page then opens. If you
are signed in and still refused, `portal.ronation.live/hub` lists every area your
account actually holds.

Minting is a **write**, so read-only staff cannot do it. On a partner governed by
their own Roblox group, that is a rank: Sleep Token's crew read the portal at
249+ and write at 253+, so the people who can work the door are deliberately not
the same set as the people who can mint a credential that works the door from
anywhere in the world.

### The three things that matter about a key

**It belongs to one organisation.** A Sleep Token key sees Sleep Token's
shows and nothing else. A ticket for anybody else's show comes back `not_found` -
not "forbidden", because whether somebody else's ticket exists is none of your
business, and those are the same answer. The scope is read from the key on our
side. **You cannot widen it from the request. There is no field for it.**

**It carries only the scopes it was minted with.** Eight of them, one per thing a key
can do:

| Scope              | Lets the key…                                                  |
| ------------------ | -------------------------------------------------------------- |
| `EVENTS_READ`      | List your shows, their tiers, capacity, seats left.            |
| `TICKETS_VERIFY`   | Check a ticket, or read what a player already holds. Changes nothing. |
| `TICKETS_REDEEM`   | Check somebody in at the door. **The scanner's scope.**        |
| `TICKETS_ISSUE`    | Reserve and gift free tickets from inside the experience.      |
| `INTENTS_WRITE`    | Hold a seat for ten minutes while a player decides. Takes no money. |
| `TICKETS_PURCHASE` | Issue a **paid** ticket on your game server's word. See below. |
| `TICKETS_VOID`     | Void a ticket, or revoke a player from a show.                 |
| `DISCORD_LINK`     | Tie a Roblox account to a Discord one via the code at /account/link. The bot's scope. |

**Tick only what the key needs.** A door scanner with `TICKETS_REDEEM` and nothing
else, if it leaks, cannot be turned into a ticket printer. That is the entire
reason scopes exist - one key per job, not one key for everything.

Calling an endpoint your key has no scope for is a **403**, never a 401. Your key
is fine; it is simply not allowed to do that. Do not go and re-copy the key - mint
one with the right boxes ticked. Scopes are fixed at mint and cannot be edited
afterwards: changing what a key can do means replacing it, deliberately.

**It is shown once.** We store a SHA-256 of the token, not the token, so nobody -
including us - can ever read it back to you. Lose it and you mint a new one; there
is no "reveal" button and there is no support request that produces one.

### Keeping it

Put it in **server** scripts only: a `Script` or a `ModuleScript` the client cannot
require. Never a `LocalScript`, never in `ReplicatedStorage`, never in a place
somebody can take a copy of it. Anybody holding the key can do everything it was
minted with, from anywhere, as you.

Revoke it the moment it leaks - the portal's **Revoke** button kills it on the very
next request, and revoked is permanent (mint a replacement rather than un-revoking).
A key you no longer recognise in the list is a key to revoke: the portal shows what
each one was named, who minted it, and when it was last used, so an unused key with
a name nobody remembers is safe to kill.

### If you were handed a key that does not start with `rnl_`

That is `GAME_API_KEY`, the original one, and it predates all of the above. It is
**unscoped** - it can verify, redeem, issue, void and revoke tickets for every show
on the platform, RNL's and every partner's alike - and it holds every scope. It is
still accepted, so nothing that uses it breaks, and it is not in the portal, so it
cannot be revoked from there.

It is on its way out. If you are wiring something up today, mint a scoped key and
use that instead. If you are maintaining something that still holds the old one,
moving it onto a scoped key is the single best thing you can do to it.

## The endpoints

| Endpoint                                   | Writes? | Scope              | Use it for                              |
| ------------------------------------------ | ------- | ------------------ | --------------------------------------- |
| `GET  /api/v1/events`                      | No      | `EVENTS_READ`      | What shows are coming up?               |
| `GET  /api/v1/events/<id>`                 | No      | `EVENTS_READ`      | One show: doors, room, tiers, seats left |
| `GET  /api/v1/events/<id>/seats`           | No      | `EVENTS_READ`      | Which seats are gone, live. Poll this.  |
| `GET  /api/v1/players/<robloxId>/tickets`  | No      | `TICKETS_VERIFY`   | What does this player already hold?     |
| `POST /api/v1/intents`                     | Yes     | `INTENTS_WRITE`    | **Hold a seat** while they decide.      |
| `GET  /api/v1/intents/<token>`             | No      | `EVENTS_READ`      | What is this token? (reads `launchData`) |
| `DELETE /api/v1/intents/<token>`           | Yes     | `INTENTS_WRITE`    | They said no. Give the seat back.       |
| `POST /api/v1/tickets/verify`              | No      | `TICKETS_VERIFY`   | Is this ticket good, and what is it?    |
| `POST /api/v1/tickets/redeem`              | Yes     | `TICKETS_REDEEM`   | Let them in, and burn the ticket.       |
| `POST /api/v1/tickets/reserve`             | Yes     | `TICKETS_ISSUE`    | Give this player a free ticket.         |
| `POST /api/v1/tickets/gift`                | Yes     | `TICKETS_ISSUE`    | X gives Y a ticket.                     |
| `POST /api/v1/tickets/purchase`            | Yes     | `TICKETS_PURCHASE` | They paid Robux. Issue the paid ticket. |
| `POST /api/v1/tickets/void`                | Yes     | `TICKETS_VOID`     | Cancel a ticket. They may reserve again.|
| `POST /api/v1/tickets/revoke`              | Yes     | `TICKETS_VOID`     | Cancel it, and bar them from this show. |
| `POST /api/v1/discord/link`                | Yes     | `DISCORD_LINK`     | Redeem a link code → tie Roblox to Discord. |
| `GET  /api/v1/discord/link`                | No      | `DISCORD_LINK`     | Who is linked? (`?discordId=` or `?robloxId=`) |
| `POST /api/v1/discord/unlink`              | Yes     | `DISCORD_LINK`     | Drop a link (`discordId` or `robloxId`). |

Every ticket endpoint returns the **same response shape**. That is deliberate: you
parse one shape in Luau, not nine.

**`eventId` is the id OR the slug, everywhere.** Keep one constant in your game and hand it
to everything - `"midnight-frequency"` is a great deal easier to not get wrong at 2am than
`"cmr9nedoy0001fgfa4abrsbt2"`, and both work on every endpoint that takes an event.

**`INTENTS_WRITE` is deliberately not `TICKETS_PURCHASE`.** Holding a chair cannot take a
penny off anybody; asserting a payment can. A lobby board or a seat map should be able to do
the first without being able to do the second, so they are two scopes and you should hand out
the smaller one.

## Identifying a ticket

`/verify`, `/redeem`, `/void` and `/revoke` all take the same body. Send **one** of:

```json
{ "code": "RN-4K9QW2" }                        // the code printed on the ticket
{ "robloxId": "851394804", "eventId": "..." }  // or: who is standing here
{ "username": "chrxs_dev", "eventId": "..." }  // or: the same person, by name
```

### Asking by player, not by code

Your server already knows who joined - `Player.UserId` and `Player.Name` - so it can
ask *"does this player hold a ticket for tonight?"* the moment they spawn, without
anybody typing anything. That is what `robloxId` is for, and it is the one to reach
for: **send `robloxId` whenever you have it.**

`username` exists for the times a human is doing the typing. It is resolved against
Roblox's own API into a `robloxId` before any ticket is looked up, because a
username is a label a player can change and an id is not - so somebody who renamed
the night before the show still walks through their own door. (An id sent in the
`username` field is accepted as-is.)

The endpoints that **write a new ticket** - `/reserve`, `/gift`, `/purchase` - take
`robloxId` only, and no username. Resolving a name costs a round trip to Roblox
that can fail, and a name is a label that can change: neither is a thing to hang
"who gets a ticket" on. Your game server has `Player.UserId`. Use it.

**A player lookup needs `eventId`.** One person can hold a ticket to every show we
run, so their name alone does not identify a ticket. Without it you get a `400`. A
`code`, by contrast, identifies exactly one ticket on its own - though you should
still send `eventId` with it, for the reason below.

Optional, and both worth sending:

```json
{
  "eventId": "cmr9nedoy0001fgfa4abrsbt2",  // the show THIS server is running
  "seal": "PVZFNR"                          // the 6-char seal printed on the ticket
}
```

### Always send `eventId` if you know it

Without it, the API can only answer *"is this a real ticket"* - not *"is this a
real ticket **for tonight**"*. A genuine ticket for last month's show would come
back `valid: true`. With `eventId`, a ticket for any other show is refused with
`reason: "wrong_event"`.

### The seal is optional and is not what admits anybody

`seal` is six characters printed on the ticket, derived from the ticket with a
secret key. If you send it, the response includes `ticket.sealValid`. It exists so
a crew member can eyeball a **printed or downloaded** ticket and spot a forgery
without a scanner. The database is what actually admits people - you do not need
the seal for a normal scan.

## The response

Every ticket endpoint returns HTTP 200 with this shape whenever the request was
understood. Failure to *find* a ticket is not an HTTP error - it is a 200 with
`valid: false`. So is a refusal to issue one.

```json
{
  "ok": true,
  "valid": true,
  "admit": true,
  "reason": "ok",
  "message": "Admit - VIP - Front Barrier",

  "ticket": {
    "id": "cmrijfyc500029h3m26mh212t",
    "code": "ST-4K9QW2",
    "status": "RESERVED",
    "admission": {
      "tier": "VIP - Front Barrier",
      "kind": "VIP",
      "priceRobux": 250,
      "paid": true
    },
    "activated": true,
    "activatedAt": "2026-07-13T18:40:00.000Z",
    "checkedIn": false,
    "checkedInAt": null,
    "seal": "PVZFNR",
    "sealValid": true
  },

  "event": {
    "id": "cmr9nedoy0001fgfa4abrsbt2",
    "slug": "stro-the-first-rite",
    "title": "THE FIRST RITE",
    "startsAt": "2026-08-03T19:00:00.000Z",
    "doorsAt": "2026-08-03T18:00:00.000Z",
    "venue": "The Hollow - Main Stage",
    "partnerId": "sleeptokenro"
  },

  "holder": {
    "robloxId": "851394804",
    "username": "chrxs_dev",
    "displayName": "chrxs_dev"
  }
}
```

When there is no ticket to talk about, `ticket`, `event` and `holder` are all
`null`:

```json
{ "ok": true, "valid": false, "admit": false, "reason": "not_found",
  "message": "No ticket with that code.", "ticket": null, "event": null, "holder": null }
```

The writing endpoints add one or two fields of their own **alongside** this shape,
never instead of it - `issued`, `created`, `voided`, `banned`. They are described
under each endpoint below.

### `valid` vs `admit` - the one thing to get right

**Branch on `admit`. Never on `valid`.**

- `valid` - the ticket is real and was not cancelled.
- `admit` - this person should walk through the door **right now**.

An already-checked-in ticket is `valid: true` and `admit: false`. It is a perfectly
genuine ticket; it has simply already been used, and letting a second person in on
it is the exact thing redeeming exists to prevent. A server that branches on
`valid` will happily admit an entire queue on one ticket.

### `reason`

| `reason`             | `valid` | `admit` | What happened                                    |
| -------------------- | ------- | ------- | ------------------------------------------------ |
| `ok`                 | true    | true    | Good ticket. Let them in.                        |
| `already_checked_in` | true    | false   | Real ticket, already used. Do not admit again.   |
| `cancelled`          | false   | false   | Voided, revoked, or the holder cancelled it.     |
| `not_found`          | false   | false   | No such code - or not one of your org's.         |
| `wrong_event`        | false   | false   | Real ticket, but for a different show.           |

`message` is a human sentence for the same thing. Show it to a crew member; do not
parse it - it is written for people and may be reworded.

### What kind of ticket is it?

`ticket.admission`:

- `tier` - the tier's name as it was **when the ticket was issued** ("General
  Admission", "VIP - Front Barrier"). It is a snapshot: renaming or deleting a tier
  afterwards does not change what somebody already holds.
- `kind` - `"GA"` or `"VIP"`. `VIP` means it was a priced tier. Branch on this to
  open the VIP room, spawn them on the barrier, hand out a badge.
- `priceRobux` / `paid` - what it cost. Free tickets are `0` / `false`.

> Paid (Robux) tiers are **switched off** platform-wide today, so in practice every
> live ticket is `kind: "GA"`, `paid: false`. The field is real and populated -
> build against it now and the VIP path works the day paid tiers are turned on.

### Errors

| HTTP | Body                                                | Meaning                             |
| ---- | --------------------------------------------------- | ----------------------------------- |
| 401  | `{ "ok": false, "error": "unauthorized" }`          | Missing, wrong or revoked key.       |
| 403  | `{ "ok": false, "error": "forbidden" }`             | Real key, without the scope for this.|
| 400  | `{ "ok": false, "error": "provide `code`, or …" }`  | No usable identifier sent.           |

A `403` is not a reason to re-copy your key. It means the key is fine and does not
have that scope - go and mint one that does.

`401` and `403` also carry a `hint`: a sentence saying what to do about it. Show it
to whoever is wiring this up; don't parse it.

## Reading the line-up

```
GET /api/v1/events            → every published upcoming show your key can see
GET /api/v1/events/<id>       → one show, in full. Takes the id OR the slug.
```

`/events/<id>` is what you read **before you offer anybody anything**. It gives you
the tier ids to pass to `/reserve` and `/purchase`, what each costs, and how many
are left:

```json
{
  "ok": true,
  "event": {
    "id": "cmr9nedoy0001fgfa4abrsbt2", "slug": "stro-the-first-rite",
    "title": "THE FIRST RITE", "status": "PUBLISHED",
    "startsAt": "…", "doorsAt": "…", "venue": "The Hollow - Main Stage",
    "capacity": 200, "reserved": 176, "remaining": 24, "partnerId": "sleeptokenro"
  },
  "tiers": [
    { "id": null, "name": "General Admission", "kind": "GA", "priceRobux": 0,
      "remaining": 24, "available": true,  "blockedReason": null },
    { "id": "cmr9…", "name": "VIP - Front Barrier", "kind": "VIP", "priceRobux": 250,
      "remaining": 0,  "available": false, "blockedReason": "soldout" }
  ]
}
```

**`available: false` means do not prompt for it.** `blockedReason` says why:

- `soldout` - the tier is full, or the room is.
- `locked` - it is priced, and Robux sales are off. Nobody can buy it today, and
  taking somebody's money for a ticket that cannot be issued is the worst bug in
  this whole document.
- `presale` - the whole **show** is in presale: published and readable, but not on
  sale yet. Every tier comes back this way, the event carries `presale: true` /
  `onSale: false`, and issuing refuses `not_on_sale` on every rail but a gift. Do not
  prompt anything until the organiser opens sales.

A tier `id` of `null` is the **implicit tier**: an event nobody configured tiers
for is one free General Admission. Send `tierId: null`, or leave it out entirely.

## Handing out tickets

### `POST /api/v1/tickets/reserve` - give this player a ticket

```json
{ "robloxId": "851394804", "eventId": "cmr9…", "tierId": null }
```

The player is standing in front of you and wants in. They do **not** need an
account on ronation.live - if they have never opened the site in their life, we
create one for them from their Roblox profile. They have a Roblox account, and that
is enough.

**Free tiers only.** A priced tier comes back `payment_required`: a ticket somebody
has to pay for is bought through `/purchase`, after Roblox has actually taken the
Robux. Reserving one here would be giving the room away.

Idempotent. A player who already holds a ticket for this show gets the ticket they
already hold, with `created: false`. Nobody holds two.

Adds to the response: `issued` (true/false), `created` (was a new one made).

### `POST /api/v1/tickets/gift` - X gives Y a ticket

```json
{ "robloxId": "851394804",       // who GETS it
  "fromRobloxId": "1234567",     // who GAVE it
  "eventId": "cmr9…", "tierId": null }
```

`/reserve` with a name attached, and the name is the point: a VIP seat nobody paid
for and nobody is recorded as handing out is a seat that turns up in an audit as a
mystery. The giver is stamped on the ticket and shown in the portal.

A gift **may** be a priced tier. That is a comp - a free VIP, given away - and no
Robux changes hands, which is exactly what a giveaway is. It still respects the
paid-ticket switch: if Robux sales are off for your org, its priced tiers do not
exist yet, and comping a seat in a tier that isn't supposed to exist is still
handing out a seat.

Adds to the response: `issued`, `created`, `gifted`.

### Why an issue can be refused

All three issuing endpoints answer `{ "ok": true, "issued": false, "reason": …,
"message": … }` - a 200, because the request was understood perfectly and the answer
is no.

| `reason`            | What happened                                                  |
| ------------------- | -------------------------------------------------------------- |
| `not_found`         | No such show - or not one of yours.                            |
| `unavailable`       | The show is not open for tickets (draft, or archived).         |
| `past`              | It has already happened.                                       |
| `badtier`           | No such tier on this show, or it has been deactivated.         |
| `soldout`           | The room is full.                                              |
| `tier_soldout`      | That tier is full, but others may not be.                      |
| `no_player`         | Roblox has never heard of that `robloxId`.                     |
| `revoked`           | They were **revoked** from this show. They may not have another.|
| `payments_off`      | Priced tier, and Robux sales are off. Nobody can have it.      |
| `not_on_sale`       | The show is in **presale** - visible, but not on sale yet. Every rail but a gift is refused. |
| `payment_required`  | Priced tier, on a path that collects no money. Use `/purchase`.|
| `not_purchasable`   | You called `/purchase` for a **free** tier. Don't charge them. |
| `already_owned`     | `/purchase` only. They already hold this tier or better - don't charge; refund if you did. |

## Selling tickets for Robux

### `POST /api/v1/tickets/purchase`

**Call this from `ProcessReceipt`, and nowhere else.**

```json
{ "purchaseId": "<receiptInfo.PurchaseId>",   // REQUIRED. The idempotency key.
  "robloxId":   "851394804",
  "eventId":    "cmr9…",
  "tierId":     "cmr9…",                      // REQUIRED. A priced tier.
  "robuxSpent": 250,
  "placeId":    "…", "productId": "…" }       // optional, recorded
```

#### What this endpoint trusts, and what it does not

Robux cannot be charged from a website. A real payment is a Developer Product
prompted inside your experience, and the **only** witness to it is the
`ProcessReceipt` handler on your game server. Roblox offers no server-to-server call
for us to ask *"was purchase X really paid for?"* - so we cannot check. **We take
your game server's word for it.**

That is the trust boundary, and it is worth reading twice rather than skimming:
anybody holding a key with `TICKETS_PURCHASE` can assert that anybody paid for
anything, and get a paid ticket for free. Give that scope only to a place you would
trust with your own Robux, and revoke the key the moment it leaks.

#### What it does guarantee

That a payment is honoured **exactly once**.

`purchaseId` is Roblox's own `PurchaseId`, and it is the idempotency key.
`ProcessReceipt` is explicitly at-least-once - Roblox re-delivers a receipt until
your game returns `PurchaseGranted`, and a server that crashes mid-call **will**
send it again. So:

- Send the same `purchaseId` twice and the second call returns the **same ticket**,
  `created: false`, and takes no second payment. **Retry freely.** A dropped
  response is safe to re-send, and you should re-send it.
- It is checked **before anything else can refuse it** - before the show is sold
  out, before it is past, before the tier is deactivated. Somebody who has already
  been charged must never be told they have no ticket because the room filled up
  while their receipt was in flight.
- If they already hold a ticket for this show, a payment for a **dearer** tier
  **upgrades** it (one ticket per person per show, always) - a GA holder buying VIP
  moves up, seat and all. But a payment for the **same tier or a cheaper one** is
  refused `already_owned` and **nothing is recorded**: there is no second ticket to
  give them, and banking the Robux for a ticket they already hold is theft with extra
  steps. This is the guard that stops a tier sold on **both** rails - a game pass on
  the site and a Developer Product in here - being charged twice. See below.

#### Granting the receipt

Return `Enum.ProductPurchaseDecision.PurchaseGranted` **only** once this has
answered `issued: true`. If it answers `issued: false`, do not grant - return
`NotProcessedYet` and let Roblox re-deliver.

And do not prompt at all for a tier that `GET /api/v1/events/<id>` says is
`available: false`. `payments_off` after you have taken somebody's Robux is a
refund, not an error message.

#### Do not prompt someone who already holds the ticket

A tier can be on sale on **both** rails at once - a game pass on the website and a
Developer Product in here - because it is the same seat sold in two places. So a
player can walk in already holding this show's ticket, bought on the site. Prompt
them the Developer Product for it and you have charged them twice for a ticket they
cannot hold twice.

**Before `PromptProductPurchase`, ask what they already hold** -
`GET /api/v1/players/<robloxId>/tickets?eventId=<id>` (see "What the player already
holds") - and do not prompt if they already hold this tier or a better one. Only
*offer the upgrade* to a GA holder; a VIP holder gets let in, not sold to.

This endpoint is the **backstop**, not the gate. A purchase that reaches it for a
tier they already hold at that tier or better is refused `already_owned` and nothing
is charged on our side - but Roblox has already taken the Robux by the time
`ProcessReceipt` fires, so all that is left then is a manual refund. The check above
is what stops you needing one.

> Paid tiers are switched off platform-wide today, so this endpoint answers
> `payments_off` for every priced tier right now. It is real and it works - build
> against it, and the day the switch flips, your purchase path is already correct.

## Seating, and the hold

Most shows are general admission and none of this applies to them: `seatMode` is `NONE`,
there is no map, and every endpoint behaves exactly as it did before seating existed. **If
you are integrating against an unseated show you can skip this entire section.**

A show with `seatMode` of `SECTION` or `SEAT` sells a *place*, and that changes one thing:

> **You cannot sell a numbered seat to somebody who never said which seat.**

So there is a step before the money: you **hold** the chair, and then you sell it.

### Why a hold has to exist

Between "I'll take row K seat 12" and `ProcessReceipt` firing, there is a Roblox purchase
prompt. Seconds, if they are quick. A minute if they go and check their balance.

With no hold, a second booth in a second server sees that chair as free for the whole of
that minute, sells it, and **exactly one of the two people who paid Robux gets it**. The
other has to be refunded by hand, by a human, who first has to work out that it happened.

The hold is what closes that window. It lasts **ten minutes**.

### The three calls

```
POST   /api/v1/intents            hold a seat        INTENTS_WRITE
DELETE /api/v1/intents/<token>    they said no       INTENTS_WRITE
GET    /api/v1/intents/<token>    what is this?      EVENTS_READ
```

**`POST /api/v1/intents`**

```json
{ "robloxId": "12345", "eventId": "midnight-frequency", "tierId": "cmr9…", "seatKey": "A1-K12" }
```

```json
{
  "ok": true,
  "held": true,
  "intent": {
    "token": "9f3c…",
    "expiresAt": "2026-07-14T20:10:00.000Z",
    "priceRobux": 250,
    "devProductId": "123456789",
    "seatKey": "A1-K12",
    "sectionKey": "A1",
    "seatLabel": "VIP Front · Row K · Seat 12"
  }
}
```

Three things about that response:

1. **`seatKey` is the seat they GOT, not the seat you asked for.** If somebody took it half a
   second ago they are quietly moved to the next best seat in the same tier. **Render what
   comes back.** Never render what you sent.
2. **`devProductId` is what to prompt.** Read it here rather than keeping your own map of
   tier → product; yours drifts the first time somebody re-makes a product.
3. Omit `seatKey` entirely and you get **best available** in that tier. That is not a
   fallback, it is a feature - it is exactly what the "Best available" button on the website
   does, and it runs the same code.

`held: false` means no seat was taken. `reason` says why; `seat_taken` is the one to respect
above all others - **do not prompt for payment**, there is nothing left in that tier to sell.

### Selling it

`POST /api/v1/tickets/purchase` now takes **`intentToken`**, and on a seated show it is
**required**. Without it we do not know which chair they bought, and refusing is the only
honest answer.

Unseated shows are unchanged: the token stays optional, and every booth that works today
keeps working untouched.

> **An expired hold is not a refusal.** They have already been charged - the money moved on a
> screen we do not control - so an expiry costs them **the seat they picked, not the ticket
> they paid for**. They fall back to the best available chair in the same tier and the
> purchase goes through. The only true refusal is `seat_taken`: the whole tier is gone, and
> that is the one case that needs a refund by hand.

### Giving the seat back

Call `DELETE /api/v1/intents/<token>` from `PromptProductPurchaseFinished` when
`wasPurchased == false`. Nothing breaks if you never do - the hold dies on its own - but
calling it means the next player sees the chair **now** instead of staring at a seat nobody
wants for ten minutes.

### The map

`GET /api/v1/events/<id>?include=venue` gives you the room: every section, its rows, and the
**anchor**.

The anchor is one affine transform for the whole map - `origin` (in studs), `scale`, `yaw` -
and that is what turns the 2D drawing into your 3D room. There is deliberately **not** a
transform per section: six hand-typed floats per block, in a 2D editor, with no way to see
whether they are right, *will* be wrong. One anchor is a thing a human can check.

`anchor: null` means the promoter never told us where the room is. Build the map flat, and do
not try to spawn anybody at their chair.

**Fetch the layout ONCE**, at startup. It does not change. Then poll:

`GET /api/v1/events/<id>/seats` - which chairs are gone, live. It is tiny, and it answers
**304 Not Modified** if you send back `If-None-Match`, so an idle show costs you nothing.

```json
{ "ok": true, "seatMode": "SEAT",
  "taken": ["A1-K12", "A1-K13"],
  "held":  ["A1-J4"],
  "sections": [{ "key": "PIT", "taken": 240, "capacity": 500 }] }
```

`taken` is sold. `held` is somebody mid-purchase - draw it differently if you like, but **do
not offer it**. If their hold expires the seat simply reappears as free.

### Starting on the web, finishing in the game

A buyer on the website gets a deep link:

```
roblox.com/games/start?placeId=<event.placeId>&launchData=<intent token>
```

Your game reads it back with `player:GetJoinData().LaunchData`, and then asks us what it
means:

```
GET /api/v1/intents/<token>
```

You get the show, the tier, the seat, and `ticketId` if it has already been spent - which is
how you know to show them their ticket instead of selling them a second one.

### What the player already holds

```
GET /api/v1/players/<robloxId>/tickets?eventId=<id>
```

The booth's opening question, and there was no way to ask it before. Three answers, three
different things to do:

- **nothing** → sell them a ticket.
- **GA** → *offer them the upgrade*. This is the sale that otherwise never happens: they have
  no idea VIP is still available, and you have no way to know you are talking to a GA holder.
- **VIP** → let them in. Don't try to sell them anything.

## Taking a ticket back

Both take the same body as `/verify` - a `code`, or a player + `eventId` - plus an
optional `reason` and `byName`.

### `POST /api/v1/tickets/void` - cancel it

Issued to the wrong player. A duplicate. A change of plan. The ticket is cancelled
and **the holder may reserve again immediately**, exactly as if they had cancelled
it themselves - because voiding is a statement about the *ticket*, not the person.

### `POST /api/v1/tickets/revoke` - cancel it, and bar them

Everything `/void` does, plus the part that matters: the holder is stamped, and
`/reserve`, `/gift` and `/purchase` all refuse to hand them another one for this
show. Without that, a revoke is a gesture - they click Reserve again and walk
straight back in.

The difference is what you are *saying*. Voiding says "this ticket is wrong".
Revoking says "this person is not coming". Use the second only when you mean it,
and send a `reason` - it is written down, and it is what the crew will read when
this person turns up at the door and asks why.

It bars them from **this show**. A standing ban across everything you run is the
blacklist, in the portal - a different question with a different answer.

Lifting a revocation is done in the portal, not from the game. The same key that
can ban should not quietly un-ban.

Both add to the response: `voided`, `banned`, `alreadyVoid`.

Both are idempotent, and **neither will touch a `CHECKED_IN` ticket**: they answer
`voided: false, reason: "checked_in"`. That person is already in the room -
cancelling the record now would not get them out of it, it would only make the
record lie. Whoever asked for this wants security, not a database write.

## Luau: the whole thing

```lua
local HttpService = game:GetService("HttpService")

local BASE     = "https://ronation.live"
local API_KEY  = "rnl_…"                       -- keep this OUT of client scripts
local EVENT_ID = "cmr9nedoy0001fgfa4abrsbt2"   -- the show this server is running

local function callApi(path, body)
    local ok, res = pcall(function()
        return HttpService:RequestAsync({
            Url = BASE .. path,
            Method = "POST",
            Headers = {
                ["Content-Type"] = "application/json",
                ["x-api-key"] = API_KEY,
            },
            Body = HttpService:JSONEncode(body),
        })
    end)

    -- The network failed. This is NOT "the ticket is bad" - do not turn somebody
    -- away because the wifi blinked. Let staff decide, or retry.
    if not ok or not res.Success then
        return nil, "network"
    end

    return HttpService:JSONDecode(res.Body), nil
end

--- Somebody presented `code` at the door.
local function admit(player, code)
    local data, err = callApi("/api/v1/tickets/redeem", {
        code = code,
        eventId = EVENT_ID,   -- always: this is what pins it to TONIGHT
    })

    if err == "network" then
        return false, "Couldn't reach the door system. Try again."
    end

    -- Branch on `admit`, NOT on `valid`. See the note above.
    if not data.admit then
        return false, data.message  -- "Already checked in.", "Cancelled.", …
    end

    -- They're in. `admission.kind` says what they hold.
    if data.ticket.admission.kind == "VIP" then
        -- open the VIP room, spawn on the barrier, hand out the badge…
        print(player.Name .. " is VIP: " .. data.ticket.admission.tier)
    end

    return true, data.message  -- "Checked in - General Admission"
end
```

### Kicking anyone without a ticket

```lua
game.Players.PlayerAdded:Connect(function(player)
    -- Look up by who they are, rather than asking them to type a code.
    local data, err = callApi("/api/v1/tickets/verify", {
        robloxId = tostring(player.UserId),
        eventId = EVENT_ID,
    })

    -- Fail OPEN on a network error, not closed. A blip at our end must not
    -- start kicking the entire room out of a show they paid to attend.
    if err == "network" then return end

    if not data.valid then
        player:Kick("You need a ticket for this show - get one at ronation.live")
    end
end)
```

Note that one uses `valid`, not `admit`: at the *gate* you are asking "do you hold
a ticket at all", and somebody already checked in still does. `admit` is for the
*door*, where the question is "should this ticket let another body through".

### Handing somebody a ticket at the gate

Rather than kicking them, sell them the show. They are already here.

```lua
local function reserveFor(player)

        robloxId = tostring(player.UserId),
        eventId = EVENT_ID,
        -- tierId = nil → General Admission. Read GET /api/v1/events/<id> for the rest.
    })

    if not data.issued then return false, data.message end  -- soldout, revoked, past…
```

### Selling a VIP tier, properly

```lua
local MarketplaceService = game:GetService("MarketplaceService")

-- productId → the tier it buys. Fill this in from GET /api/v1/events/<id>.
local TIER_FOR_PRODUCT = {
    [123456789] = "cmr9tierid…",   -- VIP - Front Barrier
}

MarketplaceService.ProcessReceipt = function(receipt)
    local tierId = TIER_FOR_PRODUCT[receipt.ProductId]
    if not tierId then
        -- Not one of ours. Don't grant something you don't understand.
        return Enum.ProductPurchaseDecision.NotProcessedYet
    end

    local data, err = callApi("/api/v1/tickets/purchase", {
        -- THE important field. Roblox re-delivers this receipt until you grant it,
        -- and this is what stops the re-delivery becoming a second ticket.
        purchaseId = receipt.PurchaseId,
        robloxId   = tostring(receipt.PlayerId),
        eventId    = EVENT_ID,
        tierId     = tierId,
        robuxSpent = receipt.CurrencySpent,
        placeId    = tostring(receipt.PlaceIdWherePurchased),
        productId  = tostring(receipt.ProductId),
    })

    -- Could not reach us, or we refused. Do NOT grant: Roblox will re-deliver the
    -- receipt, and /purchase is idempotent, so the retry settles it safely.
    if err == "network" or not data or not data.issued then
        return Enum.ProductPurchaseDecision.NotProcessedYet
    end

    -- They have their ticket. `data.created` is false on a re-delivery - that is
    -- success, not a duplicate, and it must still be granted or Roblox will keep
    -- sending it forever.
    return Enum.ProductPurchaseDecision.PurchaseGranted
end
```

### A walk-up booth, with seats

The whole thing. A player touches the booth, sees what they already hold, picks a seat, pays,
and sits in it.

```lua
local MarketplaceService = game:GetService("MarketplaceService")

local EVENT_ID = "midnight-frequency"

-- The map NEVER changes. Fetch it once; poll /seats for what has gone.
local venue          -- layout: sections, rows, anchor
local heldByPlayer = {}   -- [userId] = { token = …, seatKey = …, tierId = … }
local tierForProduct = {} -- [productId] = tierId   ← built from the API, not by hand

local function loadEvent()
    local data = callApi("GET", "/api/v1/events/" .. EVENT_ID .. "?include=venue")
    venue = data.venue and data.venue.layout or nil

    for _, tier in ipairs(data.tiers) do
        if tier.devProductId then
            tierForProduct[tonumber(tier.devProductId)] = tier.id
        end
    end

    return data.event.seatMode   -- "NONE" | "SECTION" | "SEAT"
end

-- What is gone. Cheap, and it 304s - keep the ETag and hand it back.
local etag
local function refreshSeats()
    local data, newEtag = callApi("GET",
        "/api/v1/events/" .. EVENT_ID .. "/seats", nil, etag)
    if not data then return end          -- 304: nothing changed, keep what you have
    etag = newEtag
    return data.taken, data.held         -- draw `held` differently. Do NOT offer it.
end

-- They picked a chair.
local function holdSeat(player, tierId, seatKey)
    local data = callApi("POST", "/api/v1/intents", {
        robloxId = tostring(player.UserId),
        eventId  = EVENT_ID,
        tierId   = tierId,
        seatKey  = seatKey,          -- omit for best available
    })

    if not data.held then
        -- seat_taken means the TIER is empty. Do not prompt for payment: there is
        -- nothing to sell them. Every other reason is worth showing as-is.
        return nil, data.message
    end

    heldByPlayer[player.UserId] = {
        token  = data.intent.token,
        seatKey = data.intent.seatKey,   -- ← what they GOT. Not what you asked for.
        tierId = tierId,
    }

    -- Free tier? There is nothing to pay. Take the ticket and stop.
    if not data.intent.devProductId then
        local t = callApi("POST", "/api/v1/tickets/reserve", {
            robloxId    = tostring(player.UserId),
            eventId     = EVENT_ID,
            tierId      = tierId,
            intentToken = data.intent.token,
        })
        heldByPlayer[player.UserId] = nil
        return t.ticket, t.message
    end

    MarketplaceService:PromptProductPurchase(player, tonumber(data.intent.devProductId))
    return data.intent   -- show them: "Holding " .. data.intent.seatLabel
end

-- They dismissed the prompt. Give the chair back NOW, not in ten minutes.
MarketplaceService.PromptProductPurchaseFinished:Connect(function(userId, _, wasPurchased)
    if wasPurchased then return end

    local held = heldByPlayer[userId]
    if not held then return end

    callApi("DELETE", "/api/v1/intents/" .. held.token)
    heldByPlayer[userId] = nil
end)

-- They paid.
MarketplaceService.ProcessReceipt = function(receipt)
    local tierId = tierForProduct[receipt.ProductId]
    if not tierId then
        return Enum.ProductPurchaseDecision.NotProcessedYet   -- not ours; don't grant it
    end

    local held = heldByPlayer[receipt.PlayerId]

    local data, err = callApi("POST", "/api/v1/tickets/purchase", {
        purchaseId  = receipt.PurchaseId,           -- the idempotency key. Non-negotiable.
        robloxId    = tostring(receipt.PlayerId),
        eventId     = EVENT_ID,
        tierId      = tierId,
        robuxSpent  = receipt.CurrencySpent,
        placeId     = tostring(receipt.PlaceIdWherePurchased),
        productId   = tostring(receipt.ProductId),

        -- REQUIRED on a seated show. If their hold expired while they were paying,
        -- send it anyway: an expired hold is not a refusal, and they will simply be
        -- given the best seat left in the tier rather than losing their ticket.
        intentToken = held and held.token or nil,
    })

    if err == "network" or not data or not data.issued then
        -- Roblox re-delivers the receipt, and /purchase is idempotent, so the retry
        -- settles it safely. NEVER grant a receipt we did not confirm.
        return Enum.ProductPurchaseDecision.NotProcessedYet
    end

    heldByPlayer[receipt.PlayerId] = nil

    -- data.ticket.seat.label  → "VIP Front · Row K · Seat 12"
    -- data.ticket.seat.world  → {x, y, z} in studs, if the promoter anchored the map.
    --                           Spawn them there.
    return Enum.ProductPurchaseDecision.PurchaseGranted
end

-- The booth's opening question.
local function greet(player)
    local mine = callApi("GET",
        "/api/v1/players/" .. player.UserId .. "/tickets?eventId=" .. EVENT_ID)

    local ticket = mine.tickets[1]
    if not ticket then
        return "browse"                       -- sell them something
    elseif ticket.kind == "GA" then
        return "upgrade", ticket              -- ← the sale that otherwise never happens
    else
        return "admit", ticket
    end
end
```

### Looking somebody up by name

For a staff command or an admin panel, where a person is typing rather than a
server reading `Player.UserId`:

```lua
--- "/hasticket chrxs_dev"
local function hasTicket(username)
```

The response's `holder` block comes back with the canonical `robloxId`, `username`

## Linking Discord to Roblox

A separate little system, for a Discord bot rather than a game server - but it speaks
the same API with the same keys, under the `DISCORD_LINK` scope.

A signed-in member opens **ronation.live/account/link** and sees a six-digit code that
rotates every 20 seconds, shown as `123 . 456`. They give it to your bot; your
bot redeems it:

```
POST /api/v1/discord/link
{ "code": "123456", "discordId": "<the invoking user's id>", "discordUsername": "name#0"? }
```

```json
{ "ok": true, "linked": true, "robloxId": "851394804",
  "username": "chrxs_dev", "displayName": "chrxs_dev" }
```

A wrong or expired code is a **200** with `linked: false` and a `reason`, not an error:

- `invalid` - wrong, expired, or already spent. One answer for all three on purpose:
  telling a guesser which of their tries grazed a real code is the one thing a
  six-digit secret cannot afford. Get a fresh code at /account/link.
- `discord_taken` - that Discord account is already linked to a **different** Roblox
  account. Refused, not moved - unlink it first.

**`discordId` MUST be the id Discord reports for whoever ran the command** - never a
value the user typed. The binding is only as honest as that.

**Why six digits is enough.** It isn't, on its own - the safety is around it: the
endpoint is key-gated (only your bot can call it) and **rate limited to 8 tries per 10
minutes per Discord id**, the code is single-use and one-per-account, and it dies in
20 seconds. So the whole space anyone can search against a live code, through a
throttled key, is tiny. A `429` with `Retry-After` means that budget is spent.

**The rest:**

```
GET  /api/v1/discord/link?discordId=<id>     → who is this? (or ?robloxId=<id>)
POST /api/v1/discord/unlink  { "discordId": "<id>" }   → drop the link (or robloxId)
```

`GET` answers `{ "ok": true, "linked": false }` when there is no link, or the same
shape as a redeem plus `discordId` / `linkedAt`. Use it for role sync or a `/whois`.
A member can also unlink themselves from /account/link.

## The manual door

Every scanner eventually dies mid-queue. The crew can check and check in a ticket
by hand, from a browser, and it makes the **same decision this API makes** - same
code path, so the laptop and the game can never disagree:

- RNL's shows: `ronation.live/company/door` (Roblox group rank 245+)
- A partner's shows: `portal.ronation.live/<slug>/door` (their crew, or RNL 250+)

Both take a typed code or a USB barcode scanner - a scanner is just a keyboard,
and the page is built for one: it clears and re-focuses the input after every
check, so you can scan a queue without touching the laptop.

Both also take a **player** instead of a code - a username or a Roblox id - for the
person who turns up having lost theirs. Same lookup as `username` above, and it
needs tonight's show picked for the same reason.

## Ticket anatomy, briefly

- **Code** - `RN-4K9QW2` (RNL) or `ST-4K9QW2` (a partner's prefix). What the
  **barcode** carries, and what you send to the API. The QR does **not** carry it
  (see below).
- **Barcode** - Code 128, down the left of the ticket. A cheap USB laser scanner
  reads it, which is what the manual door above is built for.
- **QR** - on the stub. It encodes the ticket's *URL*, not its code, so scanning it
  with a phone opens the ticket page. There is nothing to send to this API in it.
- **Reference** - the ticket's opaque id (`cmrij…`). Not secret; it is what the URL
  is addressed by.
- **Seal** - six characters, e.g. `PVZFNR`. Anti-forgery, optional to check, see
  above.
- **Terms** - the ticket terms in force for that show, frozen onto the ticket the
  moment it is issued. Your `/reserve`, `/gift` and `/purchase` calls record them
  too. Not returned by this API, and nothing to act on - it is here so you know a
  ticket your game issues carries the same record one bought on the website does.
- **Sealed until activated** - the code, barcode and QR are hidden until the holder
  activates the ticket. A reserved-but-not-activated ticket is still valid, and
  `/redeem` activates it for them.

**None of the above is how anybody actually gets in.** A player joins the experience,
your server reads `Player.UserId`, and you call `/redeem` with `robloxId` + `eventId`.
The code is the fallback for a human at a keyboard - a crew member looking somebody up
by hand on the manual door. Build the automatic path first.
